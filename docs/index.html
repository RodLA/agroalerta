AgroAlerta

Plataforma serverless de monitoreo agroclimático para el Perú. Procesa boletines de SENAMHI, extrae datos con OCR e inteligencia artificial, y los almacena estructurados en MongoDB Atlas.

Visión general

AgroAlerta automatiza la recolección y análisis de boletines de riesgo agroclimático publicados por SENAMHI (Servicio Nacional de Meteorología e Hidrología del Perú). El sistema funciona de forma completamente autónoma: se activa cada domingo, descarga los documentos, los procesa con OCR y extrae información estructurada usando Gemini AI.

Toda la infraestructura se gestiona con Terraform. No hay servidores que mantener — solo funciones Lambda, un orquestador con Step Functions y almacenamiento en S3 y MongoDB Atlas.

Serverless

Cero administración de servidores. Lambda escala automáticamente y solo se paga por ejecución.

Infrastructure as Code

Toda la infraestructura está definida en Terraform. Reproducible y versionada en Git.

IA integrada

Gemini 2.5 Flash extrae, interpreta y estructura datos climáticos desde documentos PDF.

Seguro por diseño

IAM con mínimo privilegio. Credenciales en Secrets Manager, nunca en código.

Arquitectura del sistema

El pipeline se ejecuta semanalmente. Cada etapa es una Lambda independiente orquestada por Step Functions, con retroalimentación de errores y reintentos automáticos.

EventBridge cron(0 1 ? * SUN *)
Step Functions Orquestación del pipeline
01
Lambda – Scraper

Navega el portal de SENAMHI y extrae los enlaces a los boletines PDF publicados en los últimos meses. Guarda el registro en MongoDB.

Python 3.11 ZIP deploy pymongo
02
Lambda – Downloader

Descarga cada PDF desde SENAMHI y lo sube a S3. Actualiza el estado del documento en MongoDB para evitar descargas duplicadas.

03
Lambda – OCR + IA

Convierte el PDF a imagen, georreferencia el mapa de riesgo usando puntos de control fijos y envía las imágenes a Gemini para extracción estructurada de datos.

Paso 1

Bootstrap del estado remoto

Terraform guarda el estado en S3. Ese bucket debe existir antes del primer terraform init. El script bootstrap.sh lo crea y activa el versionamiento.

Ejecutar este paso una sola vez. Si el bucket ya existe, el script dará un error de "already exists" — puedes ignorarlo y continuar. 
chmod +x scripts/bootstrap.sh
./scripts/bootstrap.sh agro-stg

Una vez creado el bucket, inicializa Terraform:

terraform init -reconfigure
El flag -reconfigure acepta la configuración actual del backend sin intentar migrar estado anterior.
Paso 2

Crear el repositorio ECR y hacer push de la imagen

La Lambda 3 usa una imagen de contenedor. AWS Lambda requiere que esa imagen exista en ECR antes de crear la función. Si ejecutas terraform apply sin la imagen, el despliegue falla.

Ubícate en la carpeta del Dockerfile:

cd scripts/stglmbagroocrprocessorue1

Define las variables y crea el repositorio:

REGION=us-east-1
REPO=stgecragroocrprocessorue1
PROFILE=agro-stg

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text --profile ${PROFILE})

echo "→ Account: ${ACCOUNT_ID}"
echo "→ Repo:    ${REPO}"

aws ecr create-repository --repository-name ${REPO} --region ${REGION} --profile ${PROFILE}
Las llaves ${} son obligatorias en zsh. Sin ellas, $REPO:latest se interpreta como ${REPO:l}atest (modificador de lowercase), generando un nombre de imagen incorrecto.

Autenticación, build y push:

aws ecr get-login-password --region ${REGION} --profile ${PROFILE} | \
  docker login --username AWS --password-stdin ${ACCOUNT_ID}.dkr.ecr.${REGION}.amazonaws.com

docker build --no-cache --provenance=false --platform linux/amd64 -t ${REPO}:latest .

docker tag ${REPO}:latest ${ACCOUNT_ID}.dkr.ecr.${REGION}.amazonaws.com/${REPO}:latest
docker push ${ACCOUNT_ID}.dkr.ecr.${REGION}.amazonaws.com/${REPO}:latest

El flag --platform linux/amd64 es necesario si compilas en Mac con Apple Silicon. Lambda corre en x86_64.

Copia la URI resultante y agrégala en terraform.tfvars:

lambda_ocr_image_uri = "123456789012.dkr.ecr.us-east-1.amazonaws.com/stgecragroocrprocessorue1:latest"
Paso 3

Terraform Apply

Vuelve a la raíz del proyecto y ejecuta:

cd ../..

terraform plan -out=tfplan
terraform apply tfplan

Terraform creará en orden: el bucket S3 de recursos, los roles IAM, el Lambda Layer, las tres Lambdas, la State Machine de Step Functions, la regla de EventBridge y los dos secretos de Secrets Manager (con valores dummy).

El archivo tfplan está en el .gitignore. No lo commitees — puede contener ARNs y datos sensibles de la cuenta.

El apply completo tarda entre 2 y 5 minutos.

Paso 4

Inyección de secretos

Terraform crea los secretos con valores dummy. Las Lambdas no funcionarán hasta que actualices estos valores manualmente en la consola de AWS.

Nunca pongas credenciales reales en terraform.tfvars ni en ningún archivo del repo. El bloque lifecycle { ignore_changes = [secret_string] } garantiza que Terraform no sobreescriba los valores que ingreses aquí.

Ve a AWS Secrets Manager en us-east-1 y actualiza cada secreto:

stgsecagromongoue1
{
  "user":     "tu_usuario",
  "password": "tu_password",
  "cluster":  "cluster0.xxxxx.mongodb.net",
  "db_name":  "agroalerta"
}
stgsecagrogeminiue1
{
  "api_key": "AIzaSy_TU_CLAVE_REAL"
}

Una vez actualizados, el pipeline está listo para ejecutarse el próximo domingo.

Módulos Terraform

s3

Bucket de recursos con cifrado AES-256 y bloqueo público. Sube automáticamente scripts Python, el layer de dependencias y el shapefile INEI.

iam_roles

Roles y políticas de mínimo privilegio para cada Lambda, Step Functions y EventBridge. Los ARNs de secretos son exactos, sin wildcards.

lambda

Tres funciones Lambda con sus respectivos CloudWatch Log Groups. Lambdas 1 y 2 comparten un Layer de dependencias Python. Lambda 3 usa imagen ECR.

step_functions

State Machine definida en JSON con templatefile() para inyectar ARNs de Lambda dinámicamente. Incluye reintentos y catch global.

eventbridge

Regla con expresión cron configurable. Trigger semanal hacia Step Functions con rol de invocación dedicado.

secrets_manager

Dos secretos inicializados con valores dummy. El bloque ignore_changes evita que Terraform sobreescriba los valores reales ingresados post-deploy.

Seguridad

Mínimo privilegio en IAM

Cada Lambda tiene su propio rol con acceso únicamente a los recursos que necesita. Los ARNs de los secretos están especificados de forma exacta en las políticas — sin wildcards.

Credenciales en Secrets Manager

MongoDB credentials y la Gemini API Key se almacenan en AWS Secrets Manager. Las Lambdas los leen en runtime usando el nombre del secreto inyectado como variable de entorno.

Valores dummy con ignore_changes

Terraform inicializa los secretos con valores temporales y luego los ignora. Esto permite actualizar el secret_string manualmente sin que el próximo terraform apply lo revierta.

Perfiles nombrados de AWS

Todos los comandos usan --profile agro-stg. El provider de Terraform también usa profile = var.aws_profile. Esto evita despliegues accidentales en la cuenta personal.

S3 con acceso público bloqueado

El bucket de recursos tiene block_public_acls = true y cifrado AES-256 activado por defecto. El bucket de estado Terraform también.

Errores frecuentes

El repositorio ECR muestra un nombre como stgecragroocrprocessorue1atest

Es un problema de zsh. La sintaxis $REPO:latest se interpreta como ${REPO:l}atest donde :l es el modificador de lowercase. Usa siempre llaves:

docker build -t ${REPO}:latest .
docker tag ${REPO}:latest ${ACCOUNT_ID}.dkr.ecr.${REGION}.amazonaws.com/${REPO}:latest
terraform init falla con error 403 Forbidden en S3

El backend de Terraform no puede usar variables (var.aws_profile), así que ignora el perfil del provider. Verifica que backend.tf tenga el perfil hardcodeado:

backend "s3" {
  bucket  = "stgs3agroterraformstateue1"
  key     = "agro-alerta/terraform.tfstate"
  region  = "us-east-1"
  encrypt = true
  profile = "agro-stg"
}
terraform init dice "Backend configuration changed"

El backend cambió respecto a la inicialización anterior. Usa -reconfigure:

terraform init -reconfigure
terraform apply falla al crear la Lambda 3 con error de imagen no encontrada

La imagen ECR debe existir antes del apply. Completa el Paso 2 (build + push) y actualiza lambda_ocr_image_uri en terraform.tfvars con la URI completa incluyendo :latest.

El docker push va a la cuenta equivocada

El ACCOUNT_ID se obtiene sin especificar perfil, tomando las credenciales por defecto del sistema. Siempre pasa el perfil al obtener el Account ID:

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text --profile ${PROFILE})
Las Lambdas se despliegan pero no procesan — MongoDB connection timeout

Los secretos en Secrets Manager todavía tienen los valores dummy de Terraform. Ve al paso 4 y actualiza stgsecagromongoue1 con las credenciales reales de tu cluster de MongoDB Atlas.
